# 游戏启动卡住修复设计

## 背景与问题

玩家点击“开始探索”后可能长期停留在“对方正在输入”。浏览器调试与接口探测确认存在两个独立阻塞点：

1. `unlockAudioOnce` 会等待 `AudioContext.resume()` 和多个 `audio.play()`；部分浏览器环境下 Promise 长时间不结束，导致开始游戏消息没有通过 WebSocket 发出。
2. 当前 Ark 模型默认启用深度思考。游戏服务只向前端发送 `Message.Content`，不展示 `ReasoningContent`，因此模型长时间推理期间页面没有任何可见内容。SDK 默认请求超时为 10 分钟，进一步放大了无反馈等待。

## 目标

- 音频初始化失败或超时时，不能阻止开始游戏或提交选择。
- 三国叙事关闭深度思考，缩短首段剧情响应时间。
- 首轮上下文必须包含明确的用户开局指令，确保模型生成剧情和三个选项。
- 模型请求必须在合理时间内结束并向前端返回可理解的错误。
- 保持现有 WebSocket 协议、剧情格式和选择交互不变。

## 方案

### 模型配置

在 Ark ChatModel 初始化处集中设置：

- `Thinking: disabled`，叙事游戏无需展示推理过程。
- 有限请求超时，避免沿用 SDK 的 10 分钟默认值。
- 保留现有模型名称、鉴权方式、温度和 TopP。

模型配置继续由 `service/ai` 单一负责，路由与游戏服务不感知供应商配置细节。

### 首轮上下文

姓名和初始身份继续放在 system 消息中，随后追加一条固定 user 消息，明确要求开始游戏、生成开局剧情并提供三个可选行动。同步与流式入口共用同一个上下文追加函数。

### 音频解锁

将音频初始化调整为“尽力而为”：

- 为 `AudioContext.resume()` 和每个 `audio.play()` 设置短超时。
- 无论成功、失败或超时，最终都结束初始化流程。
- 音频失败只记录 warning，不阻止切换游戏界面和发送 WebSocket 消息。

### 错误处理

- 模型调用超时后沿现有 WebSocket `error` 消息返回。
- 前端结束 loading 状态并显示简短错误，不保留无限等待状态。
- 日志消息以函数名开头，模型调用错误在实际处理层记录一次，避免重复输出。

## 数据流

```text
点击开始探索
  |
  +-- 音频限时解锁（失败仅降级）
  |
  +-- 切换游戏界面
  |
  +-- WebSocket 发送 start
        |
        +-- 后端创建限时、关闭深度思考的模型请求
              |
              +-- content -> 流式剧情与选项
              |
              +-- timeout/error -> WebSocket error -> 结束 loading
```

## 测试

- 单元测试验证 Ark 配置关闭深度思考并设置有限超时。
- 单元测试验证首轮上下文包含 system 消息和 user 开局指令。
- 静态前端回归测试验证开始流程不会无限等待音频 Promise。
- 运行全部 Go 测试。
- 浏览器回归验证 WebSocket 确实发送 `start` 帧、收到 `session/content/end`，并至少完成一轮选项交互。

## 非目标

- 不更换模型供应商或模型名称。
- 不调整既有 system 提示词、剧情格式或游戏规则。
- 不新增存档、属性系统或其他玩法。
